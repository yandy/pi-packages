# pi-context-insight 吞吐与延迟指标增强设计

## 目的

现有报告只用「总输出 token ÷ 模型总耗时」展示一个平均 TPS，无法反映整次会话的端到端吞吐、单次请求波动或模型延迟。本次增强在不引入新数据源的前提下补充这些视角。

## 目标

- 保留现有模型 TPS，新增活跃时间 TPS：总输出 token ÷ 扣除空闲后的活跃时间。
- 基于具有有效 usage 和正数模型时长的请求，新增最近一次、中位数、最快和最慢请求 TPS。
- 基于有效正数模型时长，新增平均与 P95 模型请求延迟。
- 在现有耗时卡中增加紧凑指标网格，以及可展开的逐请求明细表；明细展示输出 token、模型时长和 TPS，并标记估算时长。
- 中英文报告使用相同数值口径；缺失 usage、无效时长或样本不足时显示 `—`，不得输出 `NaN` 或 `Infinity`。

## 非目标与限制

- 不展示 TTFT、纯解码 TPS 或输入处理 TPS：会话条目没有流式 token 时间戳，模型总时长也不能拆分为输入与输出阶段。
- 不新增吞吐趋势图或完整百分位分布。
- 不新增报告分区，不改变现有模型 TPS 的加权平均口径，不升级报告 schema。
- 逐请求 TPS 是未加权样本统计；整体模型 TPS 仍按总输出 token 与总模型时长计算，两者不得混用。
- P95 延迟采用最近秩法；中位数在两个中间样本之间取平均。最近一次 TPS 取最后一个有效样本。

## 方案

### 已考虑的方式

1. **完整分布与趋势图**：信息最丰富，但需要新的图表、交互和更多布局空间，超出小型增强范围。
2. **只增加少量总数值**：改动最小，但无法定位请求间的吞吐与延迟波动。
3. **汇总指标加可展开逐请求明细**：同时覆盖整体表现和单次请求差异，复用现有耗时卡与步骤数据，采用此方式。

### 实现边界

- 在 `computeTiming` 中统一计算新增汇总指标，避免渲染层各自实现统计口径。
- 逐请求明细直接使用 `report.steps` 中的 `actual.output`、`durationMs` 和 `durationEstimated`；TPS 计算使用与汇总统计相同的有效性规则。
- 保留现有 donut、墙钟／空闲信息和逐步骤活跃时长条；新增内容放在同一耗时卡内。
- 补充统计计算、边界输入和中英文渲染测试，并运行该包的完整测试与类型检查。
