# peer 下限抬到 pi ≥1.5.0 与随之而来的简化（宿主契约对齐 · 版本兜底清理 · 审批并发语义）

日期：2026-11-16
状态：**待批准**
范围：`pi-ask-user`、`pi-coding-tools`、`pi-container-sandbox`、`pi-sandbox`、`pi-subagents`、`pi-todo`、`pi-vision-tools`、`pi-web-tools`（`pi-superpowers` 是 Pure Skills 包，无 `peerDependencies`，只受规范文档影响）
落点：8 个包的 `package.json` + 根 `package-lock.json` + `docs/guides/pi-package-spec.md` + `pi-sandbox/{index.ts,src/*,tests/*}` + `pi-ask-user/{index.ts,tests/*}` + `pi-coding-tools/src/tools/lsp-tools.ts` + `pi-vision-tools/src/vision.ts` + `pi-subagents/tests/ui/transcript-body.test.ts`

## 1. 意图

全仓 peer 下限自各包创建起就是 `>=0.80.2`，从未抬过。这个下限现在同时是三笔债的成因：

1. **它是假的**。`package-lock.json` 里 pi 解析到 **0.80.2**（npm 对开放 peer range 取最低满足版本），而开发机 `node_modules` 是 **1.5.2**：CI 的 `npm ci` 按 0.80.2 的类型跑 `tsc --noEmit`，本地按 1.5.2 跑。同一份代码在两边结论不同（§3.3 列出实测红点）。
2. **它逼出一批版本门控代码**，其中一部分连在 0.80.2 下都是多余的（§3.2 逐条给出宿主 API 的真实引入版本）。
3. **它让 pi-sandbox 背着一套规避宿主缺陷的并发机制**。宿主在 1.4.0 修好了并发对话框，规避层随之失去前提（§3.4、§7）。

抬下限到 `>=1.5.0` 是让「声明支持的最老宿主」「实际编译针对的宿主」「实际测试针对的宿主」三者重合，然后把它逼出来的代码删掉。

## 2. 目标 / 非目标 / 反目标

**目标**

- 8 个 Extension 包的 `@earendil-works/*` peer range 统一抬到 `>=1.5.0`，`package-lock.json` 随之解析到 1.5.x 并提交，CI 首次真正针对 1.5.x 编译与测试。
- 删除因旧下限而存在的探测、兜底、死分支与对应测试；改写以旧宿主为前提的注释与用户可见文案。
- 8 个包的 README（中英各一）明写宿主下限。理由：pi 安装扩展时对 peer range **既不校验也不告警**（`--omit=peer` / `--config.auto-install-peers=false` / `--legacy-peer-deps`，宿主 `dist/core/package-manager.js:1611-1653`；唯一的 peer 告警只针对写进 `dependencies` 的宿主包，`dist/core/resource-loader.js:52`），manifest 里的下限对用户不可见。
- pi-sandbox 的审批并发语义回到宿主语义上：删掉 FIFO 车道与 `resolveOwnChannel` 绕行，保留跨会话路由与 fail-closed。

**非目标**

- 不改任何包对外的工具行为契约（工具名、参数 schema、提示词、拒绝文案）。§6 的清理项都以「行为等价」为验收条件。
- 不回改历史 spec/plan 的论证（§8）。
- 不新增 CI 的 pi 版本矩阵，不给 `scripts/check-host-deps.mjs` 增加 range 字面量校验（该脚本明确不管 range 值，`scripts/check-host-deps.mjs:14-15`）。
- 本次不发版（§9）。

**反目标**（做到即算失败）

- 为了让 typecheck 变绿而放宽类型（`as never` / `as any` 扩面）。§5 的三处修法都要求换成宿主真实类型。
- 删兜底时把与版本无关的 **stale ctx 防护**一起删掉。后者的缺失会让扩展 factory 抛错 → pi 把整个扩展置 null → `bash`/`write`/`edit` 无沙箱裸跑（fail-open）。清单见 §6.3。
- 把「宿主 LIFO 栈」写进包内不变量。包不再对审批顺序做任何承诺（§7）。

## 3. 事实基础（全部实测于本机 pi 1.5.2）

### 3.1 下限现状与 lockfile 解析

| 位置 | 值 |
|---|---|
| 8 个包 `package.json` 的 `peerDependencies`（16 处 range 字面量） | `>=0.80.2` |
| `docs/guides/pi-package-spec.md:178`（模板）、`:451`（「当前 `>=0.80.2`」） | `>=0.80.2` |
| `package-lock.json:1002`（`node_modules/@earendil-works/pi-coding-agent`） | **0.80.2**（`pi-ai` / `pi-tui` 同） |
| `node_modules/@earendil-works/pi-coding-agent/package.json:3` | **1.5.2** |

`scripts/check-host-deps.mjs` 只校验「宿主提供包不得进 `dependencies`」「import 了就必须在 `peerDependencies` 声明」「typebox 系必须是 `*`」，**不校验 range 值**。`.github/workflows/test.yml` 无 pi 版本矩阵、无显式 pin，版本完全由 lockfile 决定；其 `lockfile-sync` job 跑 `npm install --package-lock-only` + `git diff --exit-code -- package-lock.json`，因此**抬下限的 PR 必须同时提交更新后的 lockfile**。

lock 停在 0.80.2 **不是**因为「npm 对开放 range 取最低满足版本」：实测在空目录里以 `>=0.80.2` 新建 lock，npm 解析到 **1.5.2**（最新满足版本）。committed lock 里的 0.80.2 是历史条目——它仍满足 range，`npm install` 就不重解析。因此抬下限后 `npm install` 会把 pi / pi-ai / pi-tui 一并解析到**当时的最新满足版本**（今日为 1.5.2）。**committed lockfile 就是本仓的宿主 pin**，不另设 devDependency 固定版本（宿主提供包按规范只进 `peerDependencies`，`docs/guides/pi-package-spec.md:445-451`；`scripts/check-host-deps.mjs` 禁止它们进 `dependencies`，devDep 不在其管辖内，但新增一层 pin 机制会连带改 `check-dev-deps.mjs:18` 的「4 个共享 devDep」规则与 dependabot 行为，收益为零）。

实施守卫：若解析结果高于 1.5.2，§3.3 的红点清单与 §5.5 的修法必须在新版本上重跑一遍再动手——本设计的全部实测以 1.5.2 为基线，1.5.1/1.5.2 本身就有增量（`custom()` 的 `blocked`、`Type.BigInt()`/`Type.Undefined()` 的强转恢复）。

### 3.4 并发对话框：宿主是**栈**（LIFO），不是队列

1.4.0 的修复原文（`CHANGELOG.md:286`）：

> Fixed concurrent extension `select`/`confirm`/`input`/`editor` dialogs and inline `custom()` components in interactive mode: a second dialog replaced the first and the first promise never settled; closing the visible dialog now shows the previous one again

实现（`dist/modes/interactive/interactive-mode.js`）：`extensionDialogs = []`（`:335`）→ `pushExtensionDialog`（`:2230-2234`）→ `showTopExtensionDialog` 取 `.at(-1)`（`:2244-2251`）→ `removeExtensionDialog` 仅当移除的是栈顶时才重新显示上一个（`:2236-2243`）。设计注释（`:2223-2229`）明确：*"Every dialog stays answerable, so no dialog promise is left pending."*

由此得到本设计依赖的四条宿主性质：

1. 第二个对话框不会让第一个的 promise 变孤儿：第一个被隐藏但留在栈里，栈顶关闭后重新显示并获焦（`:2241`→`:2244-2250`）。
2. 结算出口有三个，隐藏期间都有效：重新可见后作答、自身 `signal` abort（`:2263,2268-2269`）、自身 `timeout` 到期（`components/extension-selector.js:36-37`）。
3. 顺序是 **LIFO**：持续并发时早到的审批被反复压到下层。
4. `select`/`confirm`/`input`/`editor`/inline `custom()` 共用同一条栈；RPC 模式（`dist/modes/rpc/rpc-mode.js:51-84`）从来不是单槽位——每个请求一个 uuid、登记进 `pendingExtensionRequests` Map，互不影响。

残余边界（与本设计相关但不修）：`/reload` 与会话切换走 `resetExtensionUI`（`:2015-2043`），dispose 全部对话框并**刻意让 promise 保持 pending**（`:2018-2019` 注释原文）。这是 1.5.2 上唯一还能让 `ctx.ui.select` 永不 settle 的路径。删掉包内队列后，它的影响面是「那一次工具调用挂起」；若包内还留着进程级队列，它会永久堵死整条队列（§7.3）。

## 4. 方案与取舍

**选定：分三阶段，且删掉包内 FIFO 车道。**

| 方案 | 内容 | 取舍 |
|---|---|---|
| 一次做完 | 抬下限 + 修红点 + 删兜底 + 改审批并发，单 PR | 三层性质不同的改动（宿主契约对齐 / 结构简化 / 并发语义变更）混在一次变更里，出问题时无法归因到层，也无法只回滚一层 |
| **分三阶段（选定）** | A 抬下限并让 CI 真跑在 1.5.x（含修红点）→ B 删版本兜底（行为等价）→ C 审批并发语义（有行为面） | 每阶段自成一次可验收、可回滚的变更；A 之后仓库第一次处于「声明=编译=测试」同版本的状态，B/C 的问题都在这个状态上暴露 |
| 只抬下限 + 改审批 | 跳过 B | B 里有一批注释与断言在旧下限下就已经是**错的**（`getActiveTools`「较新的 API」、`edit` 的 `additionalProperties:false`），留着继续误导后来者 |

审批并发的两个选项：

| 选项 | 结果 |
|---|---|
| 保留 FIFO 车道，只删 `resolveOwnChannel` | 顺序确定（按到达），但把宿主的 pending 泄漏放大成进程级堵塞（§3.4 第 4 条）；且「一次只弹一个」需要作为包内不变量长期维护 |
| **删掉 FIFO 车道与 `resolveOwnChannel`（选定）** | 顺序交给宿主（LIFO），每个审批各自结算、互不阻塞；`/reload` 的 pending 泄漏只影响当次调用。代价：持续并发时早到的审批后处理，且用户看不到排队深度 |

## 5. 阶段 A：抬下限并让 CI 真跑在 1.5.x

### 5.0 动作

1. 8 个 `package.json` 的 16 处 `@earendil-works/*` range：`>=0.80.2` → `>=1.5.0`（`typebox` 的 `*` 不动）。取 `1.5.0` 而非 `1.5.2`：规范口径是「最小宿主版本」（`docs/guides/pi-package-spec.md:451`），本仓依赖的宿主性质最早在 1.5.0 齐备（pi-schema 校验 = 1.5.0，对话框栈 = 1.4.0）。
2. `npm install` 重解析 lockfile，提交 `package-lock.json`（`lockfile-sync` job 要求）。解析结果必须是 1.5.2；若更高，先按 §3.1 的守卫重跑红点清单。
3. `docs/guides/pi-package-spec.md:178`（模板 range）与 `:451`（「当前 `>=0.80.2`」）同步为 `>=1.5.0`。
4. 修 §3.3 的 3 处 typecheck 与 10 个版本成因的测试红点。
5. 8 个包的 `README.md` / `README.zh.md` 各加一行宿主下限（§2 目标第 4 条）：英文 `Requires pi >= 1.5.0.`，中文 `需要 pi >= 1.5.0。`，位置统一放在安装段之后。措辞逐字统一，不各包自创。

### 5.1 `pi-sandbox`：`ExtensionContext` → `ExtensionToolContext`

`src/tools.ts` 的 4 个 `execute` 包装（`:447`、`:474`、`:499`、`:540`）把形参 `ctx` 原样透传给宿主内建工具的 `execute`，宿主 1.5.x 要求第 5 参是 `ExtensionToolContext`。修法：4 处形参标注改为 `ExtensionToolContext`（从 `@earendil-works/pi-coding-agent` 具名导入类型），并检查随之可去掉的 `as never`。

约束：

- 不得用 `as never` / `as any` 把 ctx 塞进去——那会同时掩盖「宿主多给了 `tools`/`executeTool`」这件事，而包装层是否透传嵌套调用能力是下面这条决定。
- **决定**：包装层不改 `ctx`，原样透传（宿主给的 `ExtensionToolContext` 直接交给内建工具）。理由：内建工具是宿主自己构造的调用链，它拿到的 ctx 与不经沙箱时同形；沙箱层不介入 `executeTool` 语义。
- `readSessionId(ctx)`（`src/tools.ts:157-165`）与 `resolveCall(..., ctx, ...)` 的形参类型（`ToolCtxLike`，`:145-155`）是结构类型，`ExtensionToolContext extends ExtensionContext`（宿主 `types.d.ts:289`）→ 可直接接收，无需改动。

### 5.2 `pi-coding-tools`：`StringEnum` 的静态推导

`src/tools/lsp-tools.ts:1,119`：`StringEnum` 从 `@earendil-works/pi-ai` 导入。运行时宿主给扩展的是 `pi-ai-extension-view` 的 TypeBox 版（`TUnsafe<T[number]>`），但本仓 tsc 解析真实 pi-ai 包，拿到的是 pi-schema 的 `Schema<T[number]>`——不是 TypeBox 节点，`Static<TParams>` 推不出字面量，`params.operation` 变成 `unknown`（`:148` 报错）。

修法（已定）：**保持下发给模型的 JSON Schema 形状不变**（`{ type: "string", enum: [...] }`）——`StringEnum` 存在的理由就是部分提供商（Google 系）不支持 `anyOf`/`const`，因此不得换成 `Type.Union([Type.Literal(...)])`。改用 TypeBox 直接写出同形状：

```ts
operation: Type.Unsafe<"definition" | "references">({
  type: "string",
  enum: ["definition", "references"],
  description: "definition = where it's defined; references = who references it",
}),
```

与宿主 `pi-ai-extension-view.js:14-24` 的 `StringEnum` 实现同构，不依赖任何跨包 re-export，`Static<>` 正常推出字面量。同文件内其他 `StringEnum` 调用一并按此改写。

仓内另两处 `StringEnum`（`pi-subagents/src/tools/agent-tool.ts:194`、`pi-vision-tools/index.ts:62`）**本次不动**：它们的 `execute` 不依赖 `Static<>` 推字面量，在 1.5.2 下类型与运行时都正确（宿主 extension-view 与真实 pi-ai 两条 `StringEnum` 实现产出的 JSON Schema 同形，已比对）。它们当前不构成缺陷；将来若需要字面量推导，按同一写法改。

### 5.3 `pi-vision-tools`：`ProviderHeaders`

`index.ts:141` 把宿主的 `auth.headers`（`ProviderHeaders = Record<string, string | null>`）交给 `src/vision.ts:15` 声明的 `headers?: Record<string, string>`。修法：`VisionCallInput.auth.headers` 改用 `ProviderHeaders`（从 `@earendil-works/pi-ai` 导入类型），`src/vision.ts:62` 原样放进 `complete()` 的 `options`（该处已是 `Record<string, unknown>`）。

不得用 `as Record<string, string>` 抹掉 `null`：`null` 在 pi-ai 里是「删除该 header」的语义，抹掉会改变实际请求头。若下游确需纯字符串记录，用 pi-ai 的 `providerHeadersToRecord`（`dist/utils/headers.d.ts:3`）。

### 5.4 `pi-sandbox`：提权占位符的可达性重新划分

1.5.0 的 pi-schema 强制转换改变了「哪些畸形值能到达 `execute`」。实测（用 1.5.2 的 `@earendil-works/pi-schema` `compile(schema, { coerce: true })` 跑当前 declared schema：`command: string`、`timeout?: number`、`sandbox_permissions?: "workspace-write" | "danger-full-access" | null`、`justification?: string | null`）：

| 输入 | 1.5.2 校验结果 | 到达 execute 的值 |
|---|---|---|
| 省略两字段 | 通过 | 省略 |
| `sandbox_permissions: null` | 通过（schema 允许 null → **不**被丢弃） | `null` |
| `sandbox_permissions: "null"` / `"NULL"` / `""` | **通过（被强制转成 `null`）** | `null` |
| `sandbox_permissions: " null "` | 拒绝（`const` 错误） | 不到达 |
| `sandbox_permissions: "root"` | 拒绝 | 不到达 |
| `justification: "null"` | 通过（`Type.String()` 臂接受） | 字符串 `"null"` |
| `justification: null` | 通过 | `null` |
| `timeout: "30"` | 通过（转成 `30`） | `30` |
| 对照：schema 去掉 `Type.Null()` 时 `sandbox_permissions: null` | 通过，**键被丢弃** | 省略 |

- `stripEscalationPlaceholders`（`src/escalation.ts:105-121`，接在 `prepareArguments` 上）**仍然 load-bearing**，且在 1.5.x 上仍是第一道网：`prepareToolCallArguments` 先于 `validateToolArguments`（`pi-agent-core/dist/agent-loop.js:497-498`），钩子剥掉占位符后宿主的强制转换根本看不到它们。
- 但**理由变了**，注释必须重写（`src/escalation.ts:44-61`、`:70-104`；`src/tools.ts:122-131`）：旧文写「字符串占位符在 `sandbox_permissions` 的两字面量枚举上于校验期被硬拒（execute 不跑，0.80.2 与 1.0.0 实测同）」。在 1.5.x 上，因为本仓 schema 显式声明了 `Type.Null()`，`"null"`/`"NULL"`/`""` 会被宿主**转成 `null` 并放行**，不再硬拒；仍然硬拒的是带空白的形态（`" null "`、`"   "`）。`justification` 的字符串臂照旧把 `"null"` 原样送达，那一支的理由不变。
- 旧文引用的宿主内部符号 `normalizeOptionalNulls` 在 1.5.2 的 pi-coding-agent / pi-ai / pi-agent-core 三包 dist 中查无（等价行为现在在 `@earendil-works/pi-schema/dist/coerce.js:6,105,138`，规则是「optional 且 schema 拒绝 null 才丢」）。注释改为描述行为，不引宿主内部符号名。
- 钩子契约 ②（「校验按 declared schema，不按 strict wire schema」）在 1.5.x 上**必须重新实测**再定稿注释：`docs/extensions.md:174` 说明校验对象是 JSON Schema 本身，但 strict wire schema 与 declared schema 的差异（required 全含）是否影响「删键」策略，要在真实宿主链路上验一次（配方见 `pi-sandbox/docs/superpowers/specs/2026-10-02-denial-first-escalation-design.md` §4.3）。实测前不改代码。

| 同一请求内 `select` → `input` 串行 await | `escalation-broker.ts:135-152`；`tools.ts:183-192` | 两步式审批（Deny 后收理由）本身的形状。旧文「必须在同一个 FIFO 任务内，否则排队中的下一个 select 会顶掉理由弹窗」的前提消失（§3.4 第 1 条：只会压栈，不会顶掉），改写为「同一请求内串行」 |

### 7.3 语义变更（需要写进注释与 README）

- 并发审批的可见顺序由宿主决定，是 **LIFO**：最新的审批先获得焦点，早先的在栈里等它关闭后重新显示（`interactive-mode.js:2244-2251`）。包不再对顺序做任何承诺。
- 每个审批各自结算，互不阻塞；不再有进程级队列，因此 `/reload` 造成的 pending 泄漏（§3.4 第 4 条）只影响当次工具调用，不会堵死后续所有审批。
- RPC 模式下并发审批表现为客户端同时收到多条 `extension_ui_request`（协议本就这么设计，`rpc-mode.js:51-84`），各自独立结算。
